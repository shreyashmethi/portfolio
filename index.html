Production models

Three systems I run for a Fortune 500 car rental company. The client stays unnamed; every number here comes from production.

A loop that keeps only proven changes

I led this program

A Claude agent reads the training code of a production model, proposes one change, retrains, and checks the result against out-of-time data. If the change beats the current best and every test still passes, it's committed. If not, it's reverted. A hard budget cap ends the run before it can overspend. The loop now covers five production models.

+9.5% Recall@20% on the propensity model, from 425 rounds that cost $31 in total

Claude API, Python, XGBoost, Optuna, pytest, Hypothesis

Propensity and no-show models

Built and maintained

Five models predict which customers will add each rental extra, and a second set flags bookings likely to be cancelled or never collected. They train on 7.5 million records with strict out-of-time splits and Platt calibration, are explained with SHAP, and are promoted through champion/challenger gates on a weekly OCI pipeline. I also found and fixed three kinds of feature leakage (in RFM ranks, lifetime-value features and cumulative counts) that had quietly inflated offline scores.

XGBoost, LightGBM, CatBoost, Optuna, SHAP, OCI Data Science, NIST AI RMF model cards

22→2 days to refresh a model, once retraining and acceptance were automated

Segmentation and fleet maintenance

Built

KMeans couldn't find stable customer groups, so I rebuilt segmentation with UMAP and Gaussian mixture models. For the rental fleet I built a predictive maintenance model tuned for PR-AUC, because breakdowns are rare and accuracy would flatter it. Both run on a Redshift-to-OCI export I wrote that keeps future data out of every training row.

Document extraction with sources

Built, VerticalServe

Vision LLMs pull structured fields out of PDF, Office, Excel and image files, following schemas written as specs. Every value comes back with a confidence score and the exact place in the source it came from, so a reviewer checks the doubtful fields instead of rereading the whole document. It ships as containers through a CodeBuild-to-ECR pipeline on AWS.

Vision LLMs, Python, Docker, AWS S3, Bedrock, ECR, CodeBuild, Secrets Manager

Offline RAG with hallucination guards

Personal project

A question-answering system for long technical documents that never touches the internet. Docling and TableFormer parse the files, Qdrant runs hybrid search, a knowledge graph links entities, and LangGraph corrective-RAG agents retry weak retrievals. Before an answer is shown, it is checked for fabricated citations, swapped acronyms and claims with no source. It runs on vLLM across two NVIDIA T4 GPUs.

3 guards between the model and the reader

LangGraph, vLLM, Qdrant, Docling, NetworkX

Agents that do an auditor's tick-and-tie: they find the same figure across a company's financial documents, work out how each version was derived, and flag the ones that don't agree. A FastAPI backend serves them, with a React interface for reviewing every match.

How I work

Three habits behind everything above.

Distrust the offline score

Out-of-time splits, calibration and a hunt for leakage come before any tuning. A model that wins in a notebook and loses in production hasn't improved.

Agents propose, tests decide

LLM agents are good at generating options and poor at judging them. I put tested gates and human review between what an agent suggests and what ships.

Every answer shows its source

An LLM answer should point to where it came from, and the system should notice when it can't. That's what the citation and provenance checks in my retrieval work are for.
